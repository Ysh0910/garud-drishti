# Alerts Contract

The alert system is the warning output layer of NETRA. It converts elevated risk + exposure into structured alerts that flow through authority review before any notification is sent.

Source: AGENTS.md §27, §28; `docs/fetures/FEATURE_Alert_Engine.md`; HACKATHON_PLAN.md §7, §11.

**Non-negotiable rule from AGENTS.md and HACKATHON_PLAN.md:**

> No single citizen report independently triggers a public emergency alert. The authority remains in the decision loop for all severe notifications. AI recommends; a human approves.

---

## 1. Alert Lifecycle

```
                  risk engine / manual trigger
                           │
                           ▼
                        CREATED
                    (candidate alert)
                           │
                           ▼
                    PENDING_APPROVAL
                  (awaiting authority review)
                           │
              ┌────────────┴────────────┐
              │                         │
        authority approves        authority rejects
              │                         │
              ▼                         ▼
           ACTIVE                   (discarded)
        (notification sent             not a state —
         or simulated)                 never created
              │
      ┌───────┴────────┐
      │                │
  risk rises       risk falls
      │                │
      ▼                ▼
  ESCALATED         RESOLVED
  (upgraded)        (closed)
```

**State definitions** (from `enums.md`):

- `CREATED` — candidate generated by risk engine rule evaluation or manually by an authority.
- `PENDING_APPROVAL` — queued for authority review; no notification sent yet.
- `ACTIVE` — approved; notification sent (real or simulated).
- `ESCALATED` — risk has risen significantly since the alert was approved; alert upgraded.
- `RESOLVED` — risk has returned to below threshold; alert closed.

**There is no "REJECTED" state for an alert.** A rejected candidate is discarded without creating a stored alert record. This is distinct from report status.

## 2. Alert Trigger Rules

All thresholds are configurable in `configs/dynamic_risk.yaml` (`alert_thresholds`).

### Rule 1 — Critical threshold breach

```
IF current_risk >= critical_risk_threshold (default 81)
AND zone exposure >= exposure_threshold (configurable)
THEN CREATE candidate alert at severity CRITICAL
```

### Rule 2 — Early warning (forecast-based)

```
IF current_risk < critical_risk_threshold
AND risk_24h >= critical_risk_threshold
THEN CREATE candidate alert at severity HIGH (early warning)
```

### Rule 3 — Rapid escalation

```
IF risk_state transitions from ELEVATED → HIGH or HIGH → CRITICAL rapidly
THEN ESCALATE existing ACTIVE alert
```

All rules create `PENDING_APPROVAL` candidates; none auto-transition to `ACTIVE` without authority action.

---

## 3. Deduplication

From AGENTS.md §28:

- A zone that already has an `ACTIVE` alert does not generate a new alert if risk remains in the same band.
- A zone whose risk increases significantly (e.g., crosses from HIGH to CRITICAL) triggers an `ESCALATED` transition on the existing alert.
- A zone whose risk drops below the lower threshold triggers a `RESOLVED` transition.
- Deduplication key: `(zone_id or cell_id, alert_type)`.

## 4. Alert Object

### `AlertResponse`

```
{
  "alert_id":          string,        // server UUID
  "cell_id":           string | null, // the risk cell this alert covers
  "zone_name":         string | null, // human-readable zone name if available
  "severity":          RiskLevel,     // the risk level at time of alert creation
  "state":             AlertState,    // current lifecycle state
  "trigger_reason":    string,        // human-readable description of why this alert was created
  "trigger_rule":      string,        // machine-readable rule ID: "RULE_1_CRITICAL" | "RULE_2_EARLY_WARNING" | "RULE_3_ESCALATION" | "MANUAL"
  "risk_score_at_creation": integer,  // 0–100
  "risk_score_current":     integer | null,  // current score, null if not updated
  "created_at":        ISO 8601 UTC string,
  "updated_at":        ISO 8601 UTC string,
  "approved_by":       string | null, // authority user ID; null until approved
  "approved_at":       ISO 8601 UTC string | null,
  "resolved_at":       ISO 8601 UTC string | null,
  "notification":      NotificationSummary | null
}
```

### `NotificationSummary`

```
{
  "channel":          string,   // "SMS" | "IN_APP" | "SIMULATED"
  "sent_at":          ISO 8601 UTC string | null,
  "recipient_count":  integer | null,
  "delivery_status":  "PENDING" | "SENT" | "FAILED" | "SIMULATED"
}
```

In development, `channel` must be `"SIMULATED"` and real SMS must never be sent. This is enforced by the `SMS_MODE=mock` environment variable defined in `infrastructure/docker/docker-compose.yml`.

## 5. Alert Endpoints

### List alerts

```
GET /api/v1/alerts
```

Query parameters:
- `state` — filter by `AlertState`, optional
- `severity` — filter by `RiskLevel`, optional
- `cell_id` — filter by zone, optional
- `since` — ISO 8601 UTC, optional

Response:

```
{
  "alerts": AlertResponse[],
  "total":  integer
}
```

### Create alert (manual — authority only)

```
POST /api/v1/alerts
Content-Type: application/json
```

Request body:

```
{
  "cell_id":        string,
  "severity":       RiskLevel,
  "trigger_reason": string
}
```

Manual alerts are created directly in `PENDING_APPROVAL` state. `trigger_rule` is set to `"MANUAL"`.

Response: `AlertResponse`

### Acknowledge / Approve

```
POST /api/v1/alerts/{alert_id}/acknowledge
```

Transitions `PENDING_APPROVAL` → `ACTIVE`. Triggers simulated notification. Response: updated `AlertResponse`.

### Resolve

```
POST /api/v1/alerts/{alert_id}/resolve
```

Transitions `ACTIVE` or `ESCALATED` → `RESOLVED`. Response: updated `AlertResponse`.
